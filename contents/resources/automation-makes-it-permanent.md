# The Fixity Check

**From the episode:** *Process automation makes a process permanent.*

Automating a process is a decision about permanence, and it usually gets made
while everyone is looking at hours saved. This page asks the permanence question
before the concrete goes down.

- **What it is:** one table, one column per process you are considering automating.
- **Who fills it in:** whoever signs off the automation, with somebody who does the
  work today in the room — the second row needs their memory, not yours.
- **When:** before approving the build. Not after the pilot.
- **Time:** about twenty minutes for two processes.

## How to fill it in

1. **One column per process.** Name it the way the people who do it name it, not
   the way the proposal names it.
2. **Row one — who does it today.** A role, or a name. If the answer is "it varies",
   write *varies*; that is a real finding and it changes row two.
3. **Row two is the whole check.** The last three times this process changed: what
   changed, and who changed it. Real events. *"Ade added the second approval step
   after the duplicate invoice"* is an entry. *"It has evolved over time"* is not.
   **If you cannot fill in three, write how many you could fill in.** Zero is a
   legitimate answer and it is the one that most changes the decision.
4. **Row three — what it would take to change it after automating.** Who would have
   to be asked, what would break downstream, whose quarter it would need. An
   estimate in weeks is fine here; a guess dressed as a plan is not. **"We do not
   know yet" is a legal answer** — write it, and notice that you are about to
   automate something whose cost of change nobody can state.
5. **Row four — is fixity what you want?** Yes for a process that should be
   identical every time. No for one that is still being argued about.

## The check

| | Process 1 | Process 2 |
|---|---|---|
| Who does it today | | |

| What changing it would take *after* automating | | |
| Do we want this frozen? (yes / no / not yet) | | |
| If not yet — what would have to settle first? | | |

### One filled column, as an example

*This is an example, not a benchmark. Your rows will look nothing like it.*

| | **Example: monthly supplier reconciliation** |
|---|---|
| Who does it today | Finance ops, one person, with a checklist |
| Last three times it changed — what, and who | (1) Second approver added after a duplicate payment — finance lead. (2) Currency rounding rule changed — the person doing it, unrecorded. (3) One supplier moved to a different file format — ops, by hand |
| What changing it would take *after* automating | Not known. Two downstream reports read the output |
| Do we want this frozen? | **Not yet** |
| If not yet — what would have to settle first? | The rounding rule needs a decision on paper. It has changed twice with no record of who decided |

## How to read what you wrote

- **Three changes and three different people** means the process is still being
  argued about. Automating now freezes whichever version is winning this month.
- **Zero changes in a year** means the process is settled. Fixity is a feature. Go.
- **An empty row three** is the most valuable empty cell on the page: you are about
  to buy a permanence whose price nobody can state.
- **"Not yet" in row four is not a no.** It is a list of things to settle first, and
  the last row is that list.

## The reframe this protects you from

A proposal built on hours saved is answering *can we*. This page asks *is this the
version we want to be stuck with* — and the two questions have different answers
often enough to be worth twenty minutes.
